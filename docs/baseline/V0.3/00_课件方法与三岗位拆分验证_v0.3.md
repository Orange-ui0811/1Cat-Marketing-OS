## 2. 是否需要Agent

| 工作 | 形态 | 判断 |
|---|---|---|
| 对证据作语义分类、识别冲突/缺口并规划补证 | 有界Agent | 输入不完整、需多步判断且要结合对象版本和适用条件 |
| 研究用户、竞品、渠道并形成带反证的候选 | 有界Agent | 来源与环境变化大，不能只用固定规则 |
| 生成定位、Claim、产品资产和四平台内容候选 | 有界Agent | 需要语义生成、边界判断与人类共创 |
| 理解跨中心目标、协商承诺、暴露依赖和组织升级 | 长期数字岗位 | 需要持续使命、上下文和动态协作，不是一次性工作流节点 |
| 对象版本、状态合法性、幂等、权限和审计 | 普通软件/规则自动化 | 规则确定，必须由Runtime可靠执行 |
| 检查必填字段、固定阈值、明确规则去重 | 规则自动化 | 规则可编码；Agent只能解释异常或组织人工处理 |
| 正式批准、事实确认、预算、客户承诺和询盘判断 | 人类 | 责任、关系、风险或不可逆性要求人类最终判断 |

结论：三个数字岗位均有持续职责和动态判断价值；确定性控制不包装成Agent，正式责任不转移给Agent。

## 3. 七项拆分检验

| 检验 | PMA vs BGA | 专业岗位 vs MO | 结论 |
|---|---|---|---|
| 目标是否不同 | 产品可信与商业化表达 vs 内容/渠道/线索增长 | 专业产物 vs 跨岗位协作完整 | 明显不同 |
| 知识领域是否不同 | 产品/R&D/市场研究 vs 品牌/渠道/增长 | 领域知识 vs 组织承诺与治理 | 明显不同 |
| 数据边界是否不同 | 产品证据、Fact、Claim | BGA含内容、平台结果、去敏LeadStub；MO只读最小摘要 | 明显不同 |
| 行动权限是否不同 | 候选、补证、产品审核准备 | BGA可准备发布与登记LeadStub；MO可跨岗位提议和升级 | 明显不同 |
| 风险等级是否不同 | 事实与承诺风险 | 品牌/发布/隐私风险；MO为责任遗漏与越权协调风险 | 明显不同 |
| 是否需要独立验证 | 产品表达由产品Owner把关，成品由品牌Owner批准 | MO不能验收自己推动的专业结果 | 需要人类制衡 |
| 并行是否有价值 | 产品/市场研究与渠道/内容研究可并行 | MO跟踪依赖时专业岗位可继续安全工作 | 有明显价值 |

三岗位在至少五项上存在稳定差异，因此拆分成立。新增第四个Reviewer Agent没有独立业务Owner、数据边界和必要制衡收益，首期由人类审核更合适。

## 4. 不继续拆分的能力

| 能力 | 不拆原因 | 承载方式 |
|---|---|---|
| PMA内部的事实、研究、Claim、资产和审核准备 | 共享目标、数据和权限，高度连续 | 一个PMA加载不同Skill |
| BGA内部的Campaign、内容、平台Playbook、人工发布准备、LeadStub和归因 | 同属品牌增长闭环，专业Owner一致；五个平台Skill没有独立Owner或权限 | 一个BGA按需加载SKL-BG-07～11，风险动作由Tool策略限制 |
| MO内部的完整性、计划、承诺、提醒、接管和复盘 | 同属协调目标与组织元数据边界 | 一个MO加载不同Skill |
| 日历/定时提醒 | 确定性调度，不需要独立判断岗位 | Runtime调度或非关键Cron |
| 版本检查、Schema校验、幂等和审计 | 必须确定性、可恢复 | Runtime/Policy/Tool Gateway |
| 产品事实确认、内容批准和询盘判断 | 必须由人类承担最终责任 | 人类审批与接口 |

### 4.1 Skill、Delegate与岗位的边界

- Skill只是同一岗位按需加载的方法与SOP，不具有独立使命、Owner、权限或生命周期；增加Skill不等于增加岗位。
- Delegate只承担当前Run内的短期并行子任务，结果回到发起岗位；它不接受跨重启承诺，不持有独立业务权限，也不成为组织责任主体。
- Runtime校验器、调度器、Schema验证、幂等、审计和Kanban投影属于普通软件或规则自动化，不命名为数字岗位。
- 人类Reviewer承担最终专业判断和制衡；R0不存在可被转交给Reviewer Agent的独立批准权。

### 4.2 后续拆分触发器

任何新岗位或岗位拆分均为Major变更，不能通过新增profile、Skill或Delegate暗中完成。至少满足以下条件后，才重新启动七项检验：

1. 已出现持续任务量、容量瓶颈或可量化的并行收益；
2. 新职责与原岗位在七项检验中至少两至三项稳定不同；
3. 有独立且具名的人类业务Owner和风险Owner；
4. 能建立独立指标、评估集、异常接管、Profile和最小权限；
5. 拆分收益高于新增交接、延迟、成本和故障分析负担。

BGA是最可能的后续拆分候选。当真实PII、平台A2、不同Owner、独立风险区，或内容生产与增长运营的任务量和评价目标明显分离时，可评估拆为`Brand Content Agent`与`Growth Operations Agent`。在这些证据出现前，Campaign、内容、人工发布准备、LeadStub和归因仍由一个BGA以不同Skill承载。PMA和MO当前没有足够证据继续拆分。

## 5. 最小可行组合与移除检验

R0最小组合为三岗位但分阶段入职：先分别验证专业垂直切片，再验证MO协作与三岗位闭环。若移除任一岗位：

- 移除PMA：产品事实、证据、定位和产品表达重新完全依赖人工，BGA无法安全规模化；
- 移除BGA：内容、渠道、LeadStub和增长反馈失去持续数字责任；
- 移除MO：跨中心推进、依赖、提醒、接管和复盘重新由人类手工承担。

这证明三个岗位对目标工作方式有结构性价值。但在尚未完成开发和试运行前，只能称为目标设计，不能据此判定组织已达到L3。

## 6. 设计反模式检查

| 反模式 | V0.3护栏 |
|---|---|
| 用超级Agent跨越知识和权限 | 三岗位独立Profile、数据和Tool allowlist |
| 每个自动化步骤都做Agent | 状态、幂等、校验、通知由Runtime/规则承担 |
| Agent自产自批 | 所有正式状态由具名人类产生 |
| Memory当数据库 | 只存低敏偏好和责任ID提示，正式状态从权威源读取 |
| Workflow成为组织主语 | MO理解目标并组织承诺，Runtime只支撑 |
| 用生成数量代替价值 | 同时评价质量、周期、线索、风险、成本和人工接管 |
| 无日志和回退扩大自主性 | 扩权前必须完成审计、Canary、熔断、接管与事故演练 |

## 7. 设计决定

1. 保留三个Agent，不新增岗位；
2. 保留原23个Skill ID，并将用户提供的5个平台Playbook映射为SKL-BG-07～11；总计28个，每个Skill独立版本化和测试；
3. R0仅开放A1/A3及人工发布准备，不开放真实PII和平台写；
4. 正式业务责任、审批和风险Owner始终为人类；
5. 后续任何新Agent、岗位拆分、A2A、自动发布或真实PII均为Major变更，需重新做七项拆分、权限、数据、成本和业务评审；
6. 视频号Playbook只进入设计候选；上游scope未批准前保持dormant，不把第五个平台悄悄写成R0事实；
7. 当前三岗位拓扑可作为V0.3冻结候选签署，但签署前仍须接受DEC-01～08安全处置和规范文件哈希。
