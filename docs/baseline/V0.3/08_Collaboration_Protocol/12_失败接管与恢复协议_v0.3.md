# 失败、接管与恢复协议 v0.3

> 状态：`RECOVERY-PROTOCOL-FREEZE-CANDIDATE` · 支撑`GOV-05～07`、`NFR-02/03/06/12`、`UAT-06/07/14`。

## 0. 状态命名空间

- WorkCommitment唯一公共状态为`proposed/clarifying/accepted/active/waiting/submitted/fulfilled/rejected/manual_takeover/paused/cancelled`；输入、批准、依赖、反馈或风险等待原因只写入`waiting_reason`。
- `suspended/retraining/shadow/active_limited/active_extended/retired`属于DigitalRole生命周期，不得写入WorkCommitment。
- TaskAttempt的失败、unknown、取消和证据校验状态遵循`IF-AGENT-RUN-01`，Run/Attempt结果不得直接把Commitment置为`fulfilled`。
- 接管是显式`manual_takeover`迁移和`TakeoverPacket/ManualTask`证据，不另造同义公共状态。

## 1. 失败分类

| 类别 | 自动动作 | 人工点 |
|---|---|---|
| 输入/来源缺失 | `proposed→clarifying`或`active→waiting`，列最小缺口与`waiting_reason` | Owner补充、重协商或取消 |
| 事实/版本/批准冲突 | `active/waiting→paused`，停受影响下游并生成影响/重审包 | 专业Owner裁决，重建Context/权限 |
| 确定性Tool前置失败 | 不执行；Commitment保持原安全状态或转`waiting` | 技术Owner处理策略/系统，修正后建新attempt |
| 可证无副作用瞬时失败 | 按已批准策略有限重试，复用业务幂等键并新建attempt | 超策略转`manual_takeover` |
| 外部结果unknown | 禁止重试，Commitment转`paused`或`manual_takeover`并冻结对象 | 人类确认外部事实 |
| 连续失败/角色漂移 | 暂停相关Skill/能力；Commitment转`manual_takeover`并生成TakeoverPacket | 业务/技术Owner根因与岗位恢复 |
| Runtime中断 | `active/waiting`依持久状态和审计转`manual_takeover`；其他源状态保持安全或按状态机由人类处置 | 技术修复；业务继续人工 |
| PII/凭据/越权 | 立即阻断、最小化证据、Commitment转`paused/manual_takeover`并风险升级 | 数据/风险/业务Owner |
| 销售反馈不合格/缺失 | 不写询盘状态；Commitment按需转`waiting`并记录原因 | 销售补充合格反馈；MO仅准备内部候选 |
| 内容分类/批准不满足 | 不进入发布准备；Commitment转`waiting`或`paused` | 所需人类批准人按Grant合同处理 |

“连续”的具体次数和时间窗待DEC-08；在此之前任何重复同类高风险失败由人类审慎判定，不写虚构阈值。DEC-01下只有销售身份可写四种询盘状态和版本化原因码；DEC-02下提醒为`MONITOR_ONLY`且未签时限不自动外发；DEC-03下未分类外部内容需公司负责人额外Grant且高风险类别不得降级；DEC-04下四平台均`MANUAL`。

## 2. 全人工接管

1. 停止三岗位接受新Commitment和全部候选写Tool；2. 逐项按状态机进入安全路径：`active/waiting→paused/manual_takeover`，`proposed/accepted`保持待人类处置或合法转`cancelled`，`submitted`由接收者验收或退回；3. 导出不含PII的对象版本、Grant、人工发布/销售反馈缺口和unknown清单；4. 指定具名人类接管角色；5. 每项使用ManualTask与RoleHandoff继续；6. Runtime可用则仅保存审计，Runtime不可用则使用批准的人工记录载体；7. 人工操作保留对象/版本/时间/责任人和回执引用。人工接管不授权平台自动写、客户外联或Agent处理真实PII。

## 3. 恢复对账

恢复不是重放旧Session：读取最后确认状态→导入人工期间变更→比较对象/版本/Grant/销售反馈/外部结果→按状态机将可取消的过期Commitment迁移到`cancelled`，其余保留合法状态与审计→为仍需处理项生成新版本、新ContextSnapshot、新权限快照和新TaskAttempt→验证幂等键与unknown已人工裁决→Owner重新授权→进入岗位恢复路径。任何差异未解决时，`active/waiting`保持或转入`manual_takeover`，其他状态不得被强制改写。

岗位恢复必须经过Shadow：无行为/权限变化的中断修复也不得从`suspended`直接回到`active_limited/active_extended`，至少先进入`shadow`复核；SOUL、Skill、模型、Profile、权限、输出Schema或关键策略的Major变化必须走`suspended→retraining→shadow`，完成受影响岗位回归、红队、接管演练及人类签署后，才可恢复相应有限权限。Shadow期间全部输出由人类复核，四平台仍为MANUAL，提醒仍为MONITOR_ONLY，真实PII仍禁入。

## 4. 审计与演练

证据包括失败分类、WorkCommitment迁移、attempt、policy、最后确认状态、unknown、接管人、人工改动、恢复差异、Grant和岗位生命周期迁移。演练：重复EVT-08、发布回执unknown、Runtime在Handoff中断、销售反馈期间中断、伪造销售状态、提醒自动外发诱导、未分类内容漏批、高风险降级、三岗位同时暂停、恢复时Claim/资产已改、Major变更跳过retraining/Shadow、审计部分缺失和PII事故。未提供UAT-14及受影响回归证据不得进入`active_limited`；本协议不声称演练已执行或通过。
