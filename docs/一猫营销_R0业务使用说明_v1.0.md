# 一猫营销 R0 业务使用说明 v1.0

> 适用系统：1Cat Hermes OS R0 v0.1.0  
> 适用对象：公司负责人、产品营销负责人、品牌营销负责人、内容运营、人工发布负责人、销售人员  
> 系统入口：<http://localhost:8080>  
> 文档用途：指导业务人员按照已确认的营销流程完成一次从 Brief 到增长复盘的人工闭环。本文不是部署手册，也不代表系统已正式上线。

## 1. 先理解这套系统

1Cat Hermes OS不是三个聊天机器人，而是一套“人类负责决策，数字岗位负责准备候选、组织协作和沉淀证据”的营销工作台。

| 数字岗位 | 业务使命 | 主要产出 | 不负责 |
|---|---|---|---|
| PMA 产品营销 | 把产品资料转化为有证据的产品表达 | 产品事实、用户/场景研究、Claim和产品资产候选 | 批准Fact/Claim、编造事实、对外发布 |
| BGA 品牌增长 | 把已确认的产品表达转化为Campaign和平台内容 | Campaign、内容母稿、四平台候选、人工发布任务、LeadStub和归因候选 | 登录或写入平台、判定有效询盘、接触真实PII |
| MO 营销协同 | 管理目标、责任、依赖、等待、升级和复盘 | 协作计划、Commitment、交接、提醒候选、接管包和复盘候选 | 替PMA/BGA作专业结论、代替人类批准、把看板变绿当作业务成功 |

业务过程采用“数字岗位生成候选，人类审核和执行”的工作方式。Agent Run成功只表示候选已提交，不表示内容已批准、已发布、获得了询盘或完成了业务目标。

## 2. R0不可突破的边界

- 抖音、小红书、B站、公众号均为人工发布。系统不会登录平台、点击发布、回复评论或发送私信。
- 视频号不在R0范围内，`SKL-BG-11`保持休眠；不得用其他平台或自由文本绕过。
- 不输入真实姓名、手机号、邮箱、账号、私信正文、客户联系方式或含PII的链接。
- 系统只登记不透明的LeadStub引用；有效询盘状态只能由具名销售人员填写。
- 不允许Agent批准Fact、Claim、预算、促销、价格、交期、客户承诺或其他经营决定。
- 不允许把`unknown`当成“失败后自动重试”，也不允许把合成数据当作真实业绩。
- 业务是否完成只以“协作承诺”中的人类确认结果为准；Run结束、卡片生成或技术成功都不能自动完成业务。

发现边界问题时，立即暂停相关承诺或选择人工接管，并在“审计与证据”中核对拒绝记录。

## 3. 完整业务流程

```text
业务负责人提交Brief
        ↓
MO检查目标与输入完整性，建立责任和协作承诺
        ↓
PMA整理事实、证据、定位和Claim候选
        ↓
产品营销负责人审核；缺证则退回，确认后交接BGA
        ↓
BGA规划Campaign、内容母稿及四平台候选
        ↓
品牌/产品负责人审核具体对象版本
        ↓
系统创建人工发布任务
        ↓
具名人员登录平台完成操作并登记真实回执
        ↓
登记无PII LeadStub，销售人员填写询盘四状态
        ↓
MO汇总证据，形成增长复盘候选
        ↓
业务负责人决定完成、继续迭代、暂停或接管
```

## 4. 开始前的准备

正式开始一项工作前，业务负责人应准备：

- 明确的业务目标和期望结果；
- 产品、客户、活动或内容的边界；
- 可引用的产品资料和证据来源；
- 产品营销、品牌营销、人工发布、销售反馈的具名负责人；
- 需要完成的时间窗口；
- 已知风险、禁止表达和必须人工批准的事项；
- 不含真实PII的输入材料。

第一次体验建议使用明确标注为“合成演示”的内容，例如`synthetic://demo`。演示操作不得登录真实平台，也不得登记为真实业绩。

## 5. 登录和首页检查

1. 打开<http://localhost:8080>。
2. 输入管理员提供的个人账号和密码。共享环境不要多人共用同一个账号。
3. 登录后先看顶部是否显示“组织Runtime运行中”。
4. 在“运行总览”确认三个数字岗位存在，并查看：进行中承诺、Agent运行次数和待人工任务。
5. 打开“数字岗位”，确认PMA、BGA、MO的状态和R0边界。

如果Runtime未运行、岗位缺失或页面持续报错，不要继续创建业务对象，交给系统管理员检查。

## 6. 按业务流程完成一项工作

### 第一步：建立Brief和证据

进入“Brief与业务候选”，点击“新建候选”。

先创建`Brief`，建议内容至少包含：

- 业务背景和目标；
- 目标用户或业务场景；
- 期望交付物；
- 时间要求；
- 已知事实与来源；
- 禁止表达和风险；
- 成功标准以及谁负责最终验收。

有补充资料时，再以`证据`类型创建对象。在`SourceRef`中填写可追踪的来源引用；演示可使用`synthetic://demo/...`。不要把来源只写成“网上看到”“同事说过”。

完成标志：列表中能够看到Brief和必要证据，状态为`candidate`，版本和来源数量可见。

### 第二步：由MO组织目标和责任

进入“协作承诺”，点击“新建承诺”。

填写：

- 事项名称：用业务结果命名，例如“完成新品核心卖点候选”；
- 建议责任岗位：先选择PMA；
- 期望结果：写清交付物、证据标准、禁止事项和验收人。

新建后状态为`proposed`。具名负责人确认内容与责任后，点击“接受”；准备开始时点击“启动”。如果目标或责任不清，不要先接受再补内容，应先补充Brief或重新创建清晰的承诺。

常用状态含义：

| 状态 | 业务含义 | 下一步负责人 |
|---|---|---|
| `proposed` | 待确认的责任建议 | 被建议负责人或业务Owner |
| `accepted` | 责任和验收条件已接受，尚未开始 | 责任岗位/人类负责人 |
| `active` | 正在执行 | 当前责任岗位 |
| `waiting` | 等待证据、批准、反馈或依赖 | 等待对象的具名Owner |
| `submitted` | 候选结果已提交，等待人类验收 | 业务验收人 |
| `fulfilled` | 人类确认业务承诺已经完成 | 业务Owner |
| `paused` | 因风险或业务决定暂停 | 暂停决定人 |
| `manual_takeover` | 数字岗位停止推进，由人类接管 | 接管人 |

### 第三步：启动PMA生成产品表达候选

先完成项目专用模型认证；未认证时，真实Agent推理可能不可用。进入“Agent运行”，点击“启动Agent”：

1. 选择刚刚接受或启动的Commitment；
2. 岗位选择“PMA 产品营销”；
3. 在任务说明中引用Brief、证据和期望输出；
4. 明确要求“只生成候选，不作正式批准；缺少证据时列出缺口”。

提交后查看Run状态：

- `queued/running`：正在处理；
- `evidence_accepted`：技术执行和结构校验完成，候选已送审；
- `unknown`：结果无法确认，需要人类核对，不得盲目重试。

PMA输出应由业务人员在“Brief与业务候选”中沉淀为`fact`、`claim`或相关证据对象。每一项事实和Claim都应有SourceRef，不得把模型生成文字直接当成批准后的产品事实。

完成标志：PMA Commitment进入`submitted`，产品营销负责人已获得可审核的事实、Claim或产品资产候选。

### 第四步：产品营销负责人审核

负责人逐项检查：

- 事实是否能回溯到可靠来源；
- Claim是否超出证据；
- 是否混入价格、交期、促销、法律承诺或其他需额外批准的内容；
- 是否存在版本过期、互相冲突或缺少证据；
- 是否含真实PII。

需要修改时，不点击“确认完成”；让承诺回到继续处理的路径，或新建清晰的修订承诺。需要跨岗位传递时，进入“交接与批准”，点击“新建交接”，选择Commitment、发送岗位、接收者和交接目的。

交接只表示材料已发送，不表示接收者已认可，更不表示事实或Claim已经批准。

### 第五步：建立BGA承诺并生成Campaign与内容

产品表达满足当前人工审核要求后，在“协作承诺”中为BGA建立新承诺，例如：

- 事项名称：完成某Campaign及四平台内容候选；
- 责任岗位：BGA 品牌增长；
- 期望结果：Campaign、内容母稿、平台适配稿、风险标签和人工发布准备。

接受后，在“Agent运行”中选择BGA，任务说明中引用已审核对象的ID和版本，并写明目标平台。R0允许的平台只有：抖音、小红书、B站、公众号。

在“Brief与业务候选”中沉淀：

1. `campaign`：目标、受众、主题、渠道组合、节奏、判断指标和风险；
2. `content`：内容母稿或具体平台候选；
3. 必要的`evidence`：平台规则、业务依据或内容来源。

由于BG-07～10平台源ZIP尚未完成人类权属与hash验收，当前环境中的平台Playbook激活仍为`pending`。真实业务使用前应由品牌负责人核验平台适配内容，不能把软件中存在候选生成能力理解为官方平台资产已获批准。

### 第六步：审核对象版本和签发有限批准

需要对某个候选的特定动作明确授权时，进入“交接与批准”，点击“签发批准”。

必须填写：

- 对象类型；
- 对象ID；
- 对象版本；
- 被批准的具体动作，例如`submit_review`。

批准只对所填对象、版本和动作有效。内容改版后，不得沿用旧版本批准。R0批准范围不包含平台自动发布；填写`publish`也不会赋予Agent登录或写入平台的能力。

### 第七步：创建并执行人工发布任务

内容通过当前业务审核后，进入“人工任务”，点击“新建人工发布任务”。

填写：

- 平台：抖音、小红书、B站或公众号；
- 已审核候选对象ID和版本；
- 人工操作说明；
- 具名负责人。

每个平台分别建立任务，不要把多个账号、多个平台或多个动作合成一个模糊任务。随后由具名人员在系统之外登录平台，完成最终检查和发布。

执行后回到任务列表，点击“记录回执”：

- `completed`：人类实际完成，并已核对真实结果；
- `failed`：操作失败，说明原因；
- `unknown`：无法确认平台最终结果。

只有亲自核验后才能填写`completed`。如果网络超时、页面无响应或不确定是否已发布，必须填`unknown`并人工核对，禁止重复发布。

### 第八步：登记LeadStub和销售反馈

当人工观察到内容触点或询盘时，进入“Lead与销售反馈”，点击“登记LeadStub”。

填写：

- 不透明来源引用，例如`crm://stub/opaque-id`；
- 来源触点，例如`douyin-comment`；
- 对应Campaign引用；
- 对应Content引用。

严禁填写姓名、手机号、邮箱、账号、评论/私信正文或可以直接暴露个人身份的URL。

具名销售人员核对真实业务系统后，点击“销售反馈”，选择：

| 状态 | 使用时机 |
|---|---|
| `pending` | 销售已接收，但尚未完成判断 |
| `valid` | 销售按当前业务规则确认是有效询盘 |
| `invalid` | 销售按当前业务规则确认不是有效询盘 |
| `needs_more_info` | 证据不足，需要进一步核实 |

同时填写原因码和原因码注册表版本。Agent只能读取这一结果，不能替销售判断、预测、默认或修改询盘状态。

### 第九步：由MO组织增长复盘

在“协作承诺”中为MO建立复盘承诺，责任岗位选择“MO 营销协同”。在“Agent运行”启动MO，要求其汇总：

- Brief和目标；
- PMA事实/Claim候选及审核情况；
- Campaign和内容对象版本；
- 人工发布任务及回执；
- LeadStub和销售反馈；
- 风险、等待、退回、unknown和人工接管；
- 下一轮建议和仍需人类决定的事项。

在“Brief与业务候选”中保存`review`复盘候选。复盘应区分事实、推断和待验证项，不把浏览、点赞或技术运行成功当成业务成功。

最后由业务负责人决定：

- 确认本次Commitment完成；
- 回到`active`继续迭代；
- 暂停；
- 人工接管；
- 建立下一轮PMA或BGA承诺。

只有具名验收人在“协作承诺”中对`submitted`点击“确认完成”，状态才进入`fulfilled`。

## 7. 暂停、异常与人工接管

遇到以下情况应立即暂停或接管：

- 输入或输出含真实PII、凭据或敏感链接；
- 来源证据缺失、互相冲突或版本已变化；
- 旧批准被用于新版本对象；
- Agent多次失败、角色错配或结果为`unknown`；
- 内容涉及未批准的新Claim、价格、促销、交期、客户承诺、法律/隐私或舆情；
- 有人要求系统自动发布、回复、私信、外联或启用视频号；
- Runtime中断后，人工期间可能修改过业务对象。

处理顺序：

1. 在“协作承诺”点击“暂停”或“人工接管”；
2. 停止新的Agent Run和人工发布动作；
3. 在“审计与证据”找到相关时间、Actor、动作、对象、决定和关联ID；
4. 记录当前对象ID、版本、待完成事项、风险、负责人和下一复核点；
5. 由具名Owner解决证据、批准、权限或业务决定；
6. 恢复前核对人工期间变更，必要时创建新版本和新批准；
7. 由人类点击“恢复”后再继续。

不得依靠聊天记录或Agent Memory猜测业务状态；以工作台中的Commitment、对象版本、回执和审计记录为准。

## 8. 审计与日常检查

进入“审计与证据”可检查所有关键写入、授权和拒绝。发生争议时，至少记录：

- 时间；
- Actor；
- 动作；
- 对象类型和ID；
- allow/deny决定；
- correlation ID；
- 对应对象版本、人工回执和Commitment。

建议每日开始时检查运行总览、进行中承诺、待人工任务和`unknown`结果；每日结束前确认：

- 所有`active/waiting/paused/manual_takeover`事项都有具名责任人；
- 待审核和待发布队列清楚；
- `unknown`均已转人工核对；
- 销售反馈缺口已记录但未被Agent补写；
- 风险和版本变化已经升级；
- 没有把`submitted`误当作`fulfilled`。

## 9. 一次完整体验的建议演示脚本

为避免污染真实业务，首次体验可使用下面的合成场景：

1. 创建标题为“合成新品Brief”的Brief，SourceRef填写`synthetic://demo/brief-001`；
2. 为PMA创建“整理合成产品事实与Claim候选”的承诺，接受并启动；
3. 启动PMA，要求只输出候选和证据缺口；
4. 创建一条`fact`和一条`claim`候选；
5. 新建交接，将产品表达交给BGA；
6. 为BGA创建Campaign与四平台内容候选承诺，接受并启动；
7. 创建`campaign`和`content`候选；
8. 创建一个抖音人工发布任务，但说明“仅演示，不登录真实平台”；
9. 回执选择`unknown`，说明“未执行真实发布”；
10. 创建来源为`synthetic://demo/touchpoint-001`的LeadStub；
11. 由体验账号记录`needs_more_info`销售反馈；
12. 为MO创建复盘承诺，生成`review`候选；
13. 在“审计与证据”检查整条链路；
14. 保持合成承诺为`submitted`或明确标注演示后由人类决定，不将其计入真实业绩。

## 10. 当前使用前置条件与未开放能力

- 当前软件已完成本机合成验证，但尚未正式上线。
- 真实Agent推理需要项目管理员完成`./bin/1cat auth deepseek`、通过Model Gateway
  上游验真并验证真实模型Run。
- BG-07～10平台源ZIP权属及SHA-256尚待人类验收，真实资产激活保持`pending`。
- 真实Shadow、业务Owner UAT、DEC-08、G4和安全Owner评审仍待执行。
- 自动发布、A2A、关键Cron、真实PII和生产高可用不属于R0，也不得通过运营操作自行开启。

## 11. 业务完成检查表

一项真实业务只有同时满足以下条件，才可由具名验收人确认`fulfilled`：

- [ ] Brief目标、范围、Owner和验收标准清楚；
- [ ] PMA产品事实与Claim均有来源并完成人工审核；
- [ ] BGA Campaign和内容使用的是正确对象版本；
- [ ] 所需批准与具体对象、版本、动作一致且未失效；
- [ ] 所有平台动作均由具名人类执行并登记真实回执；
- [ ] `unknown`已人工核对，没有重复发布；
- [ ] Lead只以无PII的LeadStub进入系统；
- [ ] 询盘四状态由具名销售人员填写；
- [ ] 复盘区分事实、推断和待验证项；
- [ ] 风险、等待、退回和接管记录完整；
- [ ] 审计链能够回溯业务对象、版本和人类决定；
- [ ] 业务验收人已明确确认结果，而不是仅看到Run成功。
