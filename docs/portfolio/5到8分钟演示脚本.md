# Agent Runtime 5～8 分钟演示脚本

## 演示目标

只通过正式八类页面证明：三 Agent 不是前端模拟聊天，也不是互不相关的模型调用，而是在同一
持久化 Marketing Case 中，经真实岗位 Run、人工门禁、Commitment、Handoff、版本化对象和
模拟发布形成可恢复、可观察的业务闭环。

录屏前执行 `./bin/1cat portfolio-check`。不要打开 `.env`、Secret 文件或显示 API Key。

## 0:00～0:35　定位和边界

打开 `http://127.0.0.1:8080/?view=tasks`，指出顶栏的 `SERVER SOURCE OF TRUTH`。

> 这是我实现的三 Agent 媒体业务 Runtime。正式模式下八类页面都读取服务端事实；旧界面原型
> 只能从 `?mode=prototype` 显式进入，不参与业务结果。MO 负责规划和复盘，PMA 形成
> Fact/Claim，BGA 形成 Campaign/Content，人类在关键节点确认。发布只是 simulated 回执，
> 系统不登录真实平台、不接触真实 PII。

## 0:35～2:45　三 Agent 完整业务闭环

在“任务中心”新建合成案例，或从案例历史选择已完成案例，沿八类页面演示：

```text
任务中心：Brief → 启动 MO/PMA/BGA/复盘 → 人工发布与反馈任务
协作中心：MO/PMA/BGA 频道 → 消息/附件元数据 → chat Run → 持久回复 → Handoff
决策台账：计划、产品、内容、最终方案的批准/退回/HOLD/接管
业务对象：Fact/Claim/Campaign/Content 版本 → FINAL DELIVERABLE
```

九阶段服务端链路为：

```text
Brief → MO 规划 → 人工确认 → PMA → 产品审核 → BGA → 内容审核
→ simulated 发布 → 合成反馈 → MO 复盘 → 最终方案确认
```

刷新浏览器并切换历史 Case，说明阶段、消息、对象、决定和结果都能恢复。进入“业务对象”，
打开 `FINAL DELIVERABLE`，展示 10 章正文、来源索引、版本历史和 Markdown 下载；指出
`simulated / external_effect=false / business_outcome_claimed=false`。

## 2:45～3:40　Agent 配置真正影响运行

进入“Agent 配置”，选择 MO、PMA 或 BGA：

- 展示模型参数、岗位六件套、Skill、工具权限、工作流 Prompt 和聊天 Prompt。
- 演示草稿 → 校验 → 发布；说明草稿不会泄漏到下一条 Run。
- 进入“运行诊断”，展开一条 Run 的“运行配置快照”，核对 Profile version、完整 hash、
  Prompt/Skill 来源和权限声明。

> 新工作流和聊天 Run 只绑定已发布 Profile；运行中和历史 Run 使用不可变快照。安全重试继承
> 原 Run 快照，因此一次执行不会因为后来改了配置而失去可解释性。

## 3:40～4:35　Worker 崩溃恢复

在“运行诊断”展示已有 safe-recovery Run，或执行不调用模型的演练：

```bash
.venv/Scripts/python.exe scripts/runtime_failure_drill.py --scenario safe-recovery
```

> 第一个 Worker 在外部派发前消失，Lease 过期后旧 Attempt 标记 lost，新 Attempt 执行成功。
> 所有写回都匹配当前 Attempt 与 Lease Token，所以过期 Worker 不能覆盖新结果。

## 4:35～5:20　`unknown` 安全边界

进入“异常处置”，展示 Unknown 人工对账入口；需要复现时运行：

```bash
.venv/Scripts/python.exe scripts/runtime_failure_drill.py --scenario unknown-after-dispatch
```

> 外部派发后无法确认结果时，自动重试可能制造重复副作用，所以系统进入
> `unknown/unsafe`，只允许具名人类确认成功、失败、取消或放弃。这是 Runtime 对不确定性的
> 显式建模，不是把错误吞掉。

## 5:20～6:45　全链路可观测性

从“运行诊断”按 Case 选择 Run，并打开：

- Jaeger：`http://127.0.0.1:16686`
- Grafana：`http://127.0.0.1:3000`
- Prometheus：`http://127.0.0.1:9090`

> API 创建 Run 时持久化 W3C Trace Context；Worker 恢复上下文并记录 claim、Attempt、
> Hermes 调用。MCP 独立调用使用 Span Link，不伪造父子关系。已有真实 Case 证据中，5 条保留
> Run 均能在 Jaeger 找到 API/Worker 主 Trace 和 MCP Link；Grafana v4 有 20 个面板，其中
> 9 个属于 Marketing Workflow，历史跨系统验收为 13/13。

## 6:45～7:30　收束

> 当前完整 Demo 已覆盖八类服务端操作、三 Agent 工作流和真实对话、四层历史、版本化 Profile、
> 人工门禁、完整方案、故障恢复、unknown 和观测联查。`completed` 只表示这次案例流程完成；
> 发布没有真实副作用，也不代表营销效果。动态插件、通用 DAG、Kubernetes、生产 SLO 与真实
> 平台发布仍是后续项。

## 可重复命令与证据口径

```bash
.venv/Scripts/python.exe scripts/marketing_workflow_demo.py --mode synthetic
.venv/Scripts/python.exe scripts/marketing_workflow_demo.py --mode real
```

真实模式会调用 DeepSeek 并产生费用，不进入确定性 CI。本脚本引用的真实 DeepSeek、故障和观测
数字来自仓库内既有日期证据；若演示前未重新运行，不应表述为“本次刚刚验证”。

## 录屏验收清单

- 总时长 5～8 分钟，不出现 API Key、`.env` 或个人账号信息。
- 不打开独立 Workflow 页；只用八类页面完成操作和查看结果。
- 展示一次真实岗位聊天回复及其 chat Run/Profile 快照。
- 展示九阶段 Case、三 Agent 关系和至少两个人工门禁。
- 展示 FINAL DELIVERABLE 全文、版本、来源和安全边界。
- 展示一次安全重试或两个不可覆盖 Attempt，并解释 Fencing。
- 展示 `unknown/unsafe`，说明为何不能自动重试。
- 打开一条 Case Trace 和 Grafana Marketing Workflow 区域。
- 结尾明确 simulated、无真实平台副作用、无业务效果声明。
