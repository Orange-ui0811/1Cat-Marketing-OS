# Agent Runtime 面试讲解稿

## 90 秒项目介绍

> 我做的是一个可恢复、可观测的 Agent Runtime，而不是只封装大模型 API。系统用九阶段
> Marketing Case 串起 MO 规划、PMA Fact/Claim、BGA Campaign/Content、模拟发布、反馈和
> MO 复盘；每个关键阶段由人类门禁推进。Runtime API 持久化 Commitment、Handoff、Approval 和 Run，
> Worker 再通过 PostgreSQL 原子 claim 创建不可覆盖的 Attempt，并用 Lease、Heartbeat 和
> Fencing Token 管理执行所有权。Hermes 调用 DeepSeek，同时只能通过 Organization MCP 的
> 岗位白名单写入候选对象。
>
> 我重点处理了外部副作用的不确定性：派发前崩溃可以安全重试，派发后终态无法确认时必须
> 进入 `unknown/unsafe`，不能盲目重试。实际做了 4 Worker × 20 Run 并发、Worker kill、
> PostgreSQL 短暂中断、Hermes 超时和取消演练，重复有效执行为 0。可观测性方面用
> OpenTelemetry 串联 API 和 Worker，结合 Jaeger、Prometheus、Grafana、结构化日志和数据库
> 时间线既能定位一次 Run，也能用 Case ID 关联跨人类等待的多条 Trace。真实完整 Case 的
> 跨系统联查 13/13 通过。当前结论只覆盖本机 Compose，不把它包装成生产高可用。

## 追问一：为什么它算 Runtime？

回答结构：

1. 大模型 API 只负责生成；Runtime 负责生成前后的长期工程语义。
2. 系统拥有 Run 状态机、幂等创建、持久任务状态、Attempt 历史和取消。
3. Worker 有 claim、Lease、Heartbeat、Fencing、超时与恢复。
4. 工具调用受岗位权限和上下文限制，结果进入可审计的组织对象。
5. 执行可以通过 Trace、指标、日志和 Timeline 重建。

## 追问二：Lease、Heartbeat、Fencing 分别解决什么？

- Lease：给执行所有权一个过期时间，避免 Worker 消失后任务永久卡住。
- Heartbeat：Worker 存活时延续 Lease，同时让系统观察 heartbeat lag。
- Fencing Token：即使旧 Worker 在网络恢复后继续运行，也不能用过期权威覆盖新 Attempt。

只用 Lease 不够，因为旧 Worker 可能在过期后恢复并写回；只用 Heartbeat 也不能阻止旧所有者。

## 追问三：为什么需要 `unknown`？

外部请求超时只表示“调用方没有拿到结果”，不等于“服务端没有执行”。如果工具可能发布、
扣费或写入第三方平台，自动重试会制造重复副作用。系统在记录外部派发意图后若无法确认终态，
就进入 `unknown/unsafe` 并停止自动重试，保留 Hermes Run ID、Attempt、Trace 和人工对账入口。

## 追问四：数据库中断时为什么不把 Run 标成失败？

数据库连接失败是控制面暂时不可达，并不是 Agent 业务失败。Worker 先保留内存中的执行结果，
对连接执行有上限、带 jitter 的指数退避；恢复后丢弃旧连接并重新校验
`current_attempt_id + lease_token + lease_until`。只有数据库重新确认当前所有权，旧 Worker 才能
写回。一个完整 Lease 窗口内都无法确认时则失败关闭，交给恢复扫描器。

## 追问五：4 Worker × 20 Run 证明了什么？

证明了当前本机容器、PostgreSQL `SKIP LOCKED`、Attempt 唯一历史和 Fencing 写回组合下，
20 条合成短任务没有重复有效执行。它没有证明生产吞吐、严格公平、跨主机扩展和高可用。
9/6/4/1 的分布还说明短任务会受到容器启动先后的影响，下一次容量实验应混合长短任务、扩大
样本并加入数据库连接和模型限流指标。

## 追问六：为什么 MCP Span 使用 Link？

主 Run 的 HTTP/数据库/Worker 链路可以恢复 W3C 父子上下文；但 MCP 调用可能由独立进程和
异步边界启动，可靠父 Span 不一定仍然可用。此时使用 Attempt Trace 作为 Span Link，表达
“相关但不是连续父子”，比伪造一条看似完整的 Trace 更诚实。

## 追问七：前端与 Runtime 的责任怎么分？

前端不保存整套业务事实，只保存短期会话 Token 和当前 Run 游标；刷新后重新读取服务端的
Commitment、Run、Attempt 和 Timeline。前端可以请求创建、取消或人工确认，但状态合法性、
幂等、权限和审计都由 Runtime API 决定。

## 追问八：下一步怎么演进？

优先顺序：

1. 在第二环境复现完整 Case 基线并补生产告警/SLO。
2. 将静态 MCP 白名单演进为带 Manifest、版本、Schema 和 Capability 的动态注册框架。
3. 增加工具调用账本和真正的隔离执行器。
4. 再实现最小可恢复 DAG，最后迁移关键组件到 Kubernetes。

这个顺序保持 Runtime 正确性和观测证据先于功能面积。

## 面试边界清单

主动说明：单主机、本机 Compose、合成故障注入、真实 DeepSeek 仅用于三岗位验收。

不要声称：生产高可用、跨地域调度、生产级沙箱、完整 DAG、自动平台发布、真实业务提升。
