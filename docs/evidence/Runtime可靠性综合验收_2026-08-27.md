## PostgreSQL 短暂中断

### claim 前

- Run：`run_4bbc533f19534afa92aa43761a2089ce`
- Attempt：`attempt_23397ef9562b4a3094cd4380513b9122`
- PostgreSQL 停止 6 秒期间 Worker 保持运行。
- Worker 记录 `database_unavailable`，使用带 jitter 的指数退避。
- PostgreSQL 恢复后记录 `database_recovered`，Run 进入 `evidence_accepted`。
- Attempt 数量为 1，没有把连接故障伪装成 Agent 失败。

### Heartbeat 期间

- Run：`run_8b1aab7d67224546bcfd05051cc9f15a`
- Attempt：`attempt_2124aff4bcc741b39fad8f8fa5262f91`
- Worker 在短暂断库期间不立即宣称 Lease 丢失。
- 连接恢复后必须重新执行带 `current_attempt_id + lease_token + lease_until` 的 Heartbeat。
- 只有重新验租成功才允许最终写回；本场景保持同一 Attempt 并成功完成。
- 若一个完整 Lease 窗口内仍无法确认数据库权威，Worker 会停止旧写回，由恢复扫描器决定后续状态。

## Hermes 超时与取消

Hermes 超时 Run：`run_ee02f7b8aa774f129105118785079afe`，Attempt：
`attempt_8849c4672d204e008f532cb9ec723e16`。外部 Run 已开始但终态无法确认，因此固定进入
`unknown / hermes_result_unknown / unsafe`，自动重试次数为 0。

取消 Run：`run_3ad47f4bf8dd4d47b2885aa4e4889612`，Attempt：
`attempt_06552263a87e492fbd4cd7e955f4ff01`。取消请求写入后 API 仍返回 `running`；Worker 调用
假 Hermes `/stop`，只有得到明确 `cancelled` 后才提交 Runtime `cancelled`。

## 本轮实现

- Worker 主循环捕获数据库连接中断并执行有上限、带 jitter 的指数退避，不再因短暂断库退出。
- Heartbeat 区分“数据库暂时不可用”和“Lease 已被明确拒绝”。
- 数据库恢复后丢弃旧连接池，并重新校验 Attempt、Lease Token 和 Lease 截止时间。
- 真实 Hermes 状态写回在数据库恢复前保留，不把数据库错误误写成 Agent `unknown`。
- 增加 `onecat.worker.database.unavailable` 指标和 Grafana v3 第 11 个 Panel。
- 增加 `scripts/runtime_reliability_drill.py`，统一执行并发、断库、超时和取消验收。
- Smoke 使用私有合成 Worker，与前端保存的真实 DeepSeek 开关隔离，不修改用户模型配置。

## 可重复验收

在项目根目录执行：

```bash
.venv/Scripts/python.exe scripts/runtime_reliability_drill.py \
  --scenario all --run-count 20 --worker-count 4 --database-outage-seconds 6
```

脚本会临时停止正式 Worker、短暂停止并恢复本项目 PostgreSQL、创建并删除固定名称的专用
演练容器，并在 `finally` 中恢复正式 Worker。它不会删除数据卷。

确定性回归：

```bash
.venv/Scripts/python.exe -m pytest -q
./bin/1cat smoke
```

本轮本机结果为 Python 40 通过、2 个 PostgreSQL 专用用例在 SQLite 下显式跳过；合成
Smoke 12 / 12 步通过。

## 尚未证明

- 真实 Hermes 在取消与完成极端竞态下的所有 Provider 差异。
- Kubernetes、跨主机 Worker、生产级沙箱和真实平台副作用。
